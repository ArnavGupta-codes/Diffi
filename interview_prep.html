Diffi Project Interview Guide

Comprehensive Q&A for Hackathon / Technical Interviews

1. Motivation & Product Vision

Q What was the motivation behind building Diffi?

Students often have photos of handwritten notes, specific test questions, or diagrams, and they struggle to find related practice problems using standard keyword searches. Diffi was built to solve this by utilizing Semantic Search. Instead of matching exact words, it understands the meaning of the topic and finds conceptually similar past questions, helping students prepare for exams more efficiently.

Q What problem does Diffi solve that traditional search doesn't?

Traditional SQL or keyword-based searches fail when a student searches for "Calculus derivatives" but the uploaded question was tagged as "Math chain rule". Diffi uses AI embeddings to map words to a vector space, realizing that those two concepts are semantically related, thereby returning accurate results even if the exact keywords don't match.

2. Tech Stack & Architecture Flow

Q Can you explain the tech stack you chose and why?

  • Frontend: React.js with Framer Motion. I chose React for its component-based architecture and state management, which is crucial for building a dynamic, SPA (Single Page Application) feel like the StackOverflow-style feed.
  • Backend: FastAPI (Python). Chosen for its incredible speed, native async support, and automatic API documentation. It integrates perfectly with Python-based AI and Data Science libraries.
  • Vector Database: FAISS (Facebook AI Similarity Search). A highly efficient library for similarity search of dense vectors, perfect for a fast, local hackathon prototype.
  • AI Embeddings: LangChain & HuggingFace (all-MiniLM-L6-v2). I used this lightweight transformer model because it is fast to run locally without needing expensive API calls to OpenAI, making the app highly cost-effective.

Q Walk me through the flow of a user uploading an image.

1. The user selects an image, enters a topic/tag, and submits the form via React.
2. The React app sends a multipart/form-data POST request to the FastAPI /upload/ endpoint.
3. FastAPI saves the image to the local disk and generates a unique UUID.
4. The backend stores the tag, image path, timestamp, and vote count (0) into a metadata dictionary.
5. LangChain uses the HuggingFace model to convert the text tag into a 384-dimensional vector.
6. The vector and metadata are saved into the FAISS index, which is then serialized and saved to the disk.

Q Walk me through the flow of a user searching for a question.

1. The user types a query (e.g., "Kanban board") and selects filters like "Most Voted".
2. FastAPI receives the query and converts it into a vector using the same HuggingFace model.
3. FAISS performs an L2 distance search (Similarity Search) to find the closest vectors in the database (threshold < 1.5).
4. The backend retrieves a slightly larger pool of semantic matches, and if the user requested "Most Voted" or "Newest", it sorts that pool of metadata in memory.
5. The sorted JSON response is sent back to React, which dynamically renders the StackOverflow-style feed.

3. Issues & Troubleshooting

Q What was the biggest technical challenge you faced, and how did you solve it?

Managing the FAISS index state and directory paths.
Initially, the app was double-nesting paths (saving files in backend/backend/uploads) depending on where the terminal was launched from. This led to a state mismatch where the running server held an old FAISS index in memory that expected different vector dimensions, throwing AssertionError: assert d == self.d.
The Fix: I implemented absolute path resolution using os.path.abspath(__file__) to guarantee files always save in the exact same sibling directory. I also built an auto-recovery mechanism in FastAPI that catches dimension mismatch errors, deletes the corrupted index on disk, and gracefully creates a fresh one without crashing the server.

Q How did you implement the Like/Dislike feature with a Vector Database?

Vector databases like FAISS aren't strictly designed for mutable relational data (like updating vote counts frequently). To make it work elegantly for this prototype, I used LangChain's in-memory docstore._dict.
When a user upvotes, the frontend makes a POST request with the document's UUID. The backend finds that specific document in the FAISS in-memory dictionary, increments the metadata["votes"] field, and calls save_local() to persist it back to disk.

4. Future Enhancements & Scaling

Q If you had 3 more months to work on this, how would you scale the architecture?

  • Hybrid Database Approach: FAISS is great for vectors, but terrible for mutable metadata (like votes, user IDs, views). I would introduce PostgreSQL (with SQLAlchemy) to store users, votes, and image paths, and use a dedicated Vector DB like Pinecone or Qdrant solely for the embeddings. The SQL row ID would map to the Vector ID.
  • Cloud Storage: Move image storage from the local file system to AWS S3 or Google Cloud Storage to make the backend stateless and horizontally scalable.
  • Image OCR / VLM: Instead of relying entirely on the user typing a "tag", I would use an OCR pipeline (Tesseract) or a Vision-Language Model (like GPT-4o-mini or LLaVA) to automatically extract text from the uploaded image and generate the semantic embeddings automatically.
  • Authentication: Add JWT-based user authentication so users can save questions to their profile and their votes are tied to their account to prevent duplicate voting.
